# OpenCode bridge: design and reliability

This integration exposes ChatGPT-Web2API to OpenCode as an OpenAI-compatible coding-model provider with structured tool calls.

For installation and day-to-day use, start with [`../OPENCODE.md`](../OPENCODE.md). For an autonomous coding-agent handover, use [`opencode-handover.md`](opencode-handover.md).

## Live status

The Windows path was live-validated on a real ChatGPT account on **2026-08-19**. Normal chat, a required tool-call HTTP probe, `bash`, sequential `bash -> read`, and a create/edit/read/delete cleanup workflow all completed through OpenCode. The final file workflow returned `TOOLS_FULLY_WORKING`.

The direct baseline provider (`chatgpt-web-direct`) also returned normal model responses, which isolates the tools sidecar from the Web2API browser core during diagnostics.

## Why the extra bridge exists

The core Web2API endpoint sends ordinary text through the ChatGPT web interface. OpenCode expects a coding model to return structured `tool_calls` for local operations such as reading files, editing, searching, and invoking a shell.

The OpenCode bridge performs five jobs:

1. projects OpenCode function schemas into strict model instructions;
2. translates the model's JSON tool request into OpenAI `tool_calls` SSE;
3. converts OpenCode `role=tool` messages back into visible model context;
4. coalesces and briefly replays identical logical requests while the bridge process remains alive;
5. performs one bounded corrective retry when a model falsely claims local filesystem/terminal access is unavailable despite receiving suitable OpenCode tools.

OpenCode, not ChatGPT-Web2API, executes local tools.

## Runtime layout

Normal tools path:

```text
OpenCode
  -> http://127.0.0.1:8010/v1/chat/completions
  -> AgenticOpenCodeBridge / RuntimeOpenCodeBridge
  -> http://127.0.0.1:8080/v1/chat/completions
  -> stock Web2API -> Chrome / ChatGPT web
```

Diagnostic baseline:

```text
OpenCode
  -> chatgpt-web-direct
  -> http://127.0.0.1:8080/v1/chat/completions
  -> stock Web2API -> Chrome / ChatGPT web
```

The supported launcher is generated by setup and runs the sidecar through:

```bash
chatgpt-web2api-opencode serve \
  --upstream http://127.0.0.1:8080 \
  --host 127.0.0.1 \
  --port 8010
```

The direct provider deliberately bypasses the sidecar and has `tool_call=false`.

## Separation from browser transport

The tools integration must remain external to Web2API's Chrome/CDP transport. A previous development iteration tried to compensate for sidecar symptoms with runtime monkey-patches around navigation/composer/input behavior; those patches were removed after live testing showed they made diagnosis worse.

Maintenance rule:

- if `chatgpt-web-direct` fails, debug stock Web2API response/turn reconciliation;
- if direct works but `chatgpt-web` fails, keep Chrome/CDP unchanged and debug the sidecar/protocol.

The only core fixes retained are narrow, regression-tested turn-completion/correlation fixes required for stock direct responses to return correctly.

## Tool protocol

The bridge gives the model the available function names, descriptions, and JSON schemas. When a tool is required, the model must emit one object:

```json
{"__W2A_TOOL_CALL__":true,"name":"read","arguments":{"filePath":"README.md"}}
```

The bridge validates that:

- the selected name was actually offered by OpenCode;
- `tool_choice=none`, `required`, and a named function are respected;
- arguments decode to a JSON object;
- malformed protocol output never becomes a local tool execution.

A valid request becomes a normal OpenAI tool-call response containing `index`, `id`, `type`, function name, and encoded arguments, with `finish_reason: "tool_calls"`.

The next OpenCode request contains the assistant tool call and `role=tool` result. The bridge renders those messages as explicit conversation context for ChatGPT Web, allowing the model to request another tool or produce a final response.

## False local-capability denial recovery

ChatGPT Web is not natively aware that OpenCode will execute supplied functions. In `tool_choice=auto`, a model can occasionally answer with prose such as:

```text
I can't access or modify the OpenCode filesystem from this environment.
```

while `read`, `write`, `edit`, or `bash` were actually supplied.

`AgenticOpenCodeBridge` handles this narrowly:

1. tools must actually be present;
2. the user request must explicitly ask for a local filesystem/terminal action;
3. the model response must match a false local-capability denial pattern;
4. `tool_choice=none` is never overridden;
5. exactly one corrective retry is allowed;
6. the retry changes the effective choice to `required`, forcing the model to select one offered function rather than repeat the denial.

This is intentionally not a generic retry loop and does not force ordinary conversational questions through a tool.

## Streaming model

The upstream browser turn is intentionally requested non-streaming, even when OpenCode asks for SSE. The downstream SSE connection is prepared immediately and kept alive with comment heartbeats while the browser turn completes. When the browser result is ready, the bridge emits standards-shaped OpenAI completion/tool-call chunks and `[DONE]`.

This buffering is a reliability tradeoff:

- OpenCode sees an open/healthy SSE connection during long browser work;
- a disappearing OpenCode HTTP client does not directly cancel the browser generation;
- the bridge can share one upstream task between identical reconnects;
- token-by-token browser streaming is not available.

## Disconnect and duplicate-send protection

The bridge fingerprints the logical request. Transport-only streaming fields are excluded; model, messages, tools, tool choice, authentication context, and other logical fields remain part of the key.

While the bridge process is alive:

1. the first request creates one upstream task;
2. cancellation of an awaiting client is shielded from that task;
3. an identical retry can join the existing task;
4. a successful result is briefly replayable from a bounded in-memory cache;
5. transient upstream/auth/rate-limit/server failures are not retained as successful replay entries.

This protects the common case where OpenCode loses its HTTP connection but the local bridge and Web2API continue running.

## Hard reliability boundary

Recovery state is stored in bridge memory. If the bridge process or host dies, there is currently no durable mapping from an OpenCode request to the ChatGPT conversation turn that may already have completed.

Therefore, after a bridge crash or reboot:

- do not assume the request failed;
- inspect the ChatGPT browser conversation;
- inspect the working tree and terminal side effects;
- do not blindly retry a write-capable turn.

True crash-safe reattachment would require a persistent request journal, ChatGPT conversation/turn reconciliation, and explicit idempotency semantics. It should not be approximated by automatically issuing a second SEND.

A live client-disconnect/rejoin test is still desirable after the final core fixes; the implementation is covered by targeted tests but this specific acceptance case has not yet been re-run on the user's Windows machine.

## Setup layer

`chatgpt_web2api.opencode_setup` provides:

- JSON and JSONC-aware OpenCode config updates;
- timestamped backups;
- a separate key file referenced with OpenCode's `{file:...}` syntax;
- preservation of existing provider options and models;
- optional conservative `ask` permissions for edit, bash, and external directories;
- `chatgpt-web` as the normal tools provider;
- `chatgpt-web-direct` as a no-tools diagnostic baseline;
- local or remote Web2API/bridge URLs;
- generated `.cmd` and `.sh` launchers;
- authentication and model-catalog diagnostics through `doctor`.

On Windows, `scripts/setup-opencode.ps1` additionally installs Git and a supported Python automatically when needed, creates the managed venv, updates the checkout, and starts the local stack.

The setup layer never modifies a remote Web2API server. For a remote endpoint, the user must provide a key already accepted by that server.

## Core completion fix learned during live testing

Direct OpenCode traffic exposed a stock Web2API edge case on fresh conversations: identity capture can miss the turn UUID while the browser response completes immediately. The completion detector can then resolve the conversation ID mid-loop but later fail strict backend correlation because the large OpenCode/system prompt is represented differently in the projection response.

The retained core fix is narrow:

- fresh chat only;
- no captured UUID;
- pre-send baseline had zero user messages;
- post-send mapping contains exactly one user node;
- that unique user node can act as the turn anchor even if normalized text differs;
- existing-conversation and multi-user ambiguous cases remain strict.

This allows both the completion detector and final reconciliation to agree on the same fresh-chat turn. It replaced earlier broad runtime patches and is covered by regression tests.

## Current limitations

- One model-requested tool call per model turn; multiple tools work across successive turns.
- No parallel tool-call envelope.
- No durable recovery across bridge restart or host reboot.
- Buffered rather than token-by-token browser streaming.
- Browser automation remains sensitive to ChatGPT web changes.
- OpenCode auxiliary/title/tool turns can create multiple visible ChatGPT conversations because the current bridge favors stateless full-history turns over durable browser conversation reuse.
- Long agent sessions resend substantial history/tool schema and can hit context limits.
- The bridge is intended for loopback use by default; remote deployment requires TLS, authentication, firewalling, and independent security review.

## Test and acceptance coverage

Repository tests cover:

- tool schema injection and message normalization;
- tool-choice validation and malformed calls;
- OpenAI tool-call translation and SSE framing;
- HTTP round-trip through a fake Web2API upstream;
- in-flight coalescing, replay, bounded cache, and transient-error behavior;
- local bridge authentication and SSE keepalives;
- one-shot tool-protocol repair;
- false filesystem/terminal denial recovery;
- JSONC parsing, backups, provider merging, key-file references, safety defaults, and launchers;
- fresh-chat completion/correlation regressions found during live OpenCode testing.
